# CrawlerNest Release Bundle Structure

This document describes the contents and purpose of the `releases/v0.1-demo/` bundle, the meaning of each artifact, and the reproducibility assumptions behind them.

---

## Bundle Location

```
releases/
└── v0.1-demo/
    ├── MANIFEST.txt
    ├── RELEASE_NOTES_v0.1.md
    ├── DEMO_SCRIPT_v0.1.md
    ├── VERSION_SCOPE_v0.1.md
    ├── SCREENSHOT_CHECKLIST_v0.1.md
    ├── RELEASE_STRUCTURE.md
    ├── latest_status.json
    ├── system_snapshot_<timestamp>.json
    ├── latest_failure_summary.md
    ├── diagnostics_summary.txt
    ├── smoke_release_output.txt
    └── screenshots/
        └── README.md
```

Built by: `scripts/build_demo_bundle.sh`

---

## Artifact Meanings

### `MANIFEST.txt`

A file listing of the bundle contents, generated at bundle creation time. Used to verify bundle integrity and completeness.

---

### `RELEASE_NOTES_v0.1.md`

The authoritative human-readable description of the v0.1 milestone. Contains:

- Executive summary
- Current capabilities
- Architecture summary
- Included components table
- Operational capabilities
- Diagnostics and explainability coverage
- Subject ranking support
- Readonly agent integration
- Known limitations
- Explicit non-goals
- Current maturity assessment
- Recommended future directions

This document is frozen at v0.1.

---

### `DEMO_SCRIPT_v0.1.md`

Step-by-step scripts for three demo formats:

- **3-minute demo**: health check → global rankings → system status
- **5-minute demo**: smoke test → rankings → subject rankings → diagnostics API → system status
- **10-minute technical walkthrough**: startup flow → rankings → subject rankings → diagnostics → explainability → system status → release smoke

Each step includes the command or browser action, expected output, and what to explain verbally.

---

### `VERSION_SCOPE_v0.1.md`

Defines the precise boundary of the v0.1 milestone:

- **Included**: all operational capabilities, pipeline components, API endpoints, and scripts
- **Not included**: capabilities considered but not activated in v0.1
- **Future work**: accepted directions for post-v0.1 development
- **Explicitly avoided**: deliberate out-of-scope decisions that should not be revisited without a new milestone decision

The milestone freeze statement records the exact data state at freeze time.

---

### `SCREENSHOT_CHECKLIST_v0.1.md`

A prioritized list of screenshots to capture for demo documentation:

- Required (5 must-haves)
- Operational evidence (3 screenshots)
- Diagnostics (3 screenshots)
- CI evidence (2 screenshots)
- Explainability (2 screenshots)
- Extended optional (8 screenshots)

Each entry includes route or command, recommended viewport, and recommended filename.

---

### `RELEASE_STRUCTURE.md`

This document. Describes the bundle structure, artifact meanings, snapshot role, diagnostics role, and reproducibility assumptions.

---

### `latest_status.json`

A copy of `snapshots/latest_status.json` at bundle creation time. Contains:

```json
{
  "snapshot_timestamp": "...",
  "aggregated_count": 1499,
  "source_counts": [...],
  "unresolved_total": 4,
  "drift_warning_count": 0,
  "last_aggregation_run_id": 2,
  "last_aggregation_at": "...",
  "last_aggregation_status": "finished",
  "overall_stale": false
}
```

This is a point-in-time snapshot of the system state, not a live value. It represents the system state at the last time `export_system_snapshot.py` was run.

---

### `system_snapshot_<timestamp>.json`

The most recent named snapshot file from `snapshots/`. Contains the same fields as `latest_status.json` but identified by its creation timestamp. Used for snapshot comparison and drift detection via `scripts/compare_snapshots.py`.

---

### `latest_failure_summary.md`

A copy of `reports/latest_failure_summary.md` at bundle creation time. Contains:

- Overall status table (freshness, drift warnings, regression)
- Unresolved entity count and trend
- Data staleness assessment
- Regression coverage metrics

Generated by `scripts/build_failure_summary.py`. Can be regenerated from any snapshot file without a live database.

---

### `diagnostics_summary.txt`

Output of `scripts/check_pipeline_health.py` captured at bundle creation time. A readonly diagnostic check that inspects system artifacts (snapshots, logs, reports) without querying the live database or modifying any state.

This artifact confirms the system passed its readonly health check at the time of bundle creation.

---

### `smoke_release_output.txt`

Output of `scripts/smoke_release.sh` captured at bundle creation time. Contains the results of:

1. Local environment verification
2. Spring Boot compile (`mvnw compile`)
3. Next.js build (`npm run build`)
4. Python syntax check (`py_compile`)
5. Pipeline health diagnostics (readonly)
6. Snapshot comparison validation (readonly fixtures)
7. Failure-state fixture validation (readonly fixtures)
8. API endpoint checks (skipped if Spring Boot is not running)

A `Release smoke passed.` line at the end confirms the build artifact chain is intact. This is the same script run by CI (`release-smoke.yml`).

---

### `screenshots/`

Directory for captured demo screenshots. Contains `README.md` with the priority order and filename conventions. Screenshots are not generated automatically — they must be captured manually per `SCREENSHOT_CHECKLIST_v0.1.md`.

If a screenshot cannot be captured, a `.txt` placeholder with `[missing]` is acceptable.

---

## Snapshot Role

Snapshots are the primary evidence of system state over time. They are:

- **Written by**: `scripts/export_system_snapshot.py`
- **Stored at**: `snapshots/system_snapshot_<timestamp>.json` and `snapshots/latest_status.json`
- **Read by**: `scripts/build_failure_summary.py`, `scripts/compare_snapshots.py`, `scripts/check_pipeline_health.py`
- **Not modified by**: bundle creation, smoke tests, diagnostics checks

Snapshots capture a point-in-time view of PostgreSQL aggregation state. They are readonly after creation and safe to copy into the bundle without affecting runtime state.

---

## Diagnostics Role

The diagnostics layer provides read-only observability:

- **API diagnostics** (`/api/v1/diagnostics/*`): live reads from PostgreSQL, served by Spring Boot
- **Script diagnostics** (`check_pipeline_health.py`): reads snapshot files and reports, does not query the database
- **CI fixture diagnostics**: offline assertions against committed fixture files, no live database required

The bundle captures script diagnostics at creation time. API diagnostics are live and can be queried when the stack is running.

---

## Reproducibility Assumptions

The v0.1 demo bundle is reproducible under these conditions:

1. **Local environment**: WSL2/Ubuntu with PostgreSQL 14+, Python 3.12+, Node.js ≥ 20.9, Java 17+
2. **Database credentials**: `clawer` database, `test` user, password `test`, localhost:5432
3. **Bootstrap**: `python3 -m crawlernest.run_pipeline bootstrap-postgres` initializes schemas deterministically
4. **Data load**: `python3 -m crawlernest.run_pipeline run --limit 30 --ranking-year 2026` produces consistent results from the same QS 2026 source
5. **Snapshot**: `snapshots/latest_status.json` reflects the state after the last pipeline run; regenerating it requires a live database and a fresh pipeline run
6. **CI**: both `release-smoke.yml` and `data-quality.yml` run without a live database using committed fixtures

The bundle's `latest_status.json` and `system_snapshot_*.json` are frozen at bundle creation time. To regenerate them with a fresh database state, run `scripts/export_system_snapshot.py` after a pipeline run.

---

## Bundle Creation

```bash
./scripts/build_demo_bundle.sh
```

This script is:

- **Readonly-safe**: does not modify runtime state
- **Non-destructive**: does not delete any existing data or files
- **Idempotent**: safe to run multiple times; overwrites the bundle directory
- **Missing-artifact safe**: if any artifact is missing, writes a `[missing]` marker file instead of crashing

After bundle creation, capture screenshots per `SCREENSHOT_CHECKLIST_v0.1.md` and place them in `releases/v0.1-demo/screenshots/`.
