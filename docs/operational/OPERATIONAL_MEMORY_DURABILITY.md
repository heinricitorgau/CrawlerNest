# Operational Memory Durability

This document classifies CrawlerNest operational artifacts by durability,
defines the semantics for each durability tier, and provides guidance for
how operators should read and preserve each category.

---

## Durability Tiers

| Tier | Meaning |
| --- | --- |
| **Durable** | Written once; not regenerated; authoritative historical evidence. Read as evidence of what was true at a specific point in time. |
| **Semi-durable** | Written infrequently; regenerated only when meaningful state changes occur. Read as current operational context, not continuous history. |
| **Ephemeral** | Regenerated on every maintenance session or whenever a trigger fires. Read as current-state indication only. Do not rely on previous versions. |

---

## Durable Artifacts

These artifacts are written once and should not be modified after creation.

### Named Snapshots

`snapshots/system_snapshot_YYYYMMDD_HHMMSS.json`

- Written by `export_system_snapshot.py` when a meaningful state change occurs
- Never overwritten or deleted after creation
- Append-only — accumulate as a historical timeline
- Each file is evidence of what the operator observed at that moment
- Read as: "This is what was true at this timestamp."

**Durability guarantee:** If the file exists, its contents are the original
capture. No subsequent operation should modify it.

### Release Bundle Artifacts

`releases/v0.1-demo/` (all files)

- Written by `build_demo_bundle.sh` at bundle-build time
- Semantically frozen at the MANIFEST.txt build timestamp
- Self-contained: a reader does not need the live `reports/` directory
  to interpret the bundle
- Captures confidence, caveats, smoke, freshness, and snapshot evidence
  as a coherent point-in-time record

**Durability guarantee:** Files in the bundle are the bundle-time snapshot.
Post-bundle regenerations of the same reports do not change the bundle copies.

### Phase Validation Output

`scripts/validate_maintenance_phase*.py` (output records, commit messages)

- Phase validation scripts run once per milestone to generate evidence
- Their output (printed results, commit messages) is historical evidence
- The scripts themselves are reference tools, not recurring checks
- Read as: "At this milestone, these checks passed."

## Semi-Durable Artifacts

These artifacts are regenerated infrequently — only when meaningful state
changes occur. They provide operational context rather than continuous history.

### Drift Timeline

`reports/drift_timeline.md`

- Regenerated by `build_drift_timeline.py` when new snapshots are added
- Meaningful only when the snapshot population grows
- Running it when no new snapshots exist produces identical output to the
  previous run — no information gain
- Read as: "This is the drift classification across all named snapshots."

**Semi-durable because:** The timeline accumulates as snapshots accumulate.
Each regeneration adds new classification rows. The history is preserved in
the content, not the file history.

### Freshness Escalation Report

`reports/freshness_escalation.md`

- Regenerated by `build_freshness_escalation.py` when source state changes
- At RC-1, QS freshness increases monotonically — each regeneration shows
  a higher data age
- At RC-1, THE and ARWU state is stable — regeneration shows no new information
- Read as: "This is the current escalation classification."

**Semi-durable because:** The report is accurate at the time of regeneration
but does not carry historical state across runs.

### Operational Trust Summary

`reports/operational_trust_summary.md`

- Regenerated by `build_operational_trust_summary.py` before releases and weekly
- Reflects the confidence dimensions at the time of regeneration
- Previous versions are not retained; the current version is authoritative
- Read as: "This is the current confidence posture."

**Semi-durable because:** It is regenerated on a defined cadence rather than
continuously, but it does not accumulate history.

---

## Ephemeral Artifacts

These artifacts are regenerated on every maintenance session or trigger. Each
regeneration replaces the previous version entirely. Do not treat previous
versions as evidence.

### Maintenance Calm Summary

`reports/maintenance_calm_summary.md`

- Regenerated at step [7/N] of every `maintenance_overview.sh` run
- Reflects the current posture at generation time
- Previous version has no special status — it reflected the previous session

### Maintenance Steadiness Summary

`reports/maintenance_steadiness_summary.md`

- Regenerated at step [8/N] of every `maintenance_overview.sh` run
- Same ephemeral semantics as the calm summary

### Maintenance Continuity Summary

`reports/maintenance_continuity_summary.md`

- Regenerated at step [9/N] of every `maintenance_overview.sh` run
- Same ephemeral semantics as the calm and steadiness summaries

### Maintenance Navigation Report

`reports/maintenance_navigation.md`

- Regenerated during `maintenance_overview.sh`
- Shows current report status (present/missing/empty)
- Previous version has no special status

### Latest Status Pointer

`snapshots/latest_status.json`

- Overwritten each time `export_system_snapshot.py` runs
- Is a current-state pointer, not a historical record
- Do not use it for historical analysis — use named snapshots instead

### Agent Reasoning Context

`tmp/agent-context/` (all files)

- Ephemeral AI reasoning artifacts; never authoritative
- Do not read as operational guidance

## Bundle Durability Semantics

The release bundle (`releases/v0.1-demo/`) deserves special attention because
it contains both durable and ephemeral artifacts, frozen at bundle-build time.

**Semantics:**
- Files inside the bundle are the bundle-time version of each artifact.
- A `maintenance_calm_summary.md` inside the bundle reflects the calm posture
  at bundle-build time — not the current posture.
- The bundle is the evidence record for the v0.1 release claim, not a
  continuously updated dashboard.

**Reading rule:**
- When assessing current system state: read `reports/`
- When reconstructing release-time posture: read `releases/v0.1-demo/`

**Modification rule:**
- Do not modify files inside the bundle after creation.
- Do not update the bundle to reflect post-release changes unless creating a
  new bundle (v0.2, etc.).

## Snapshot Durability Semantics

Named snapshots are the primary durable evidence layer. Their semantics:

| Property | Value |
| --- | --- |
| Creation | Once, by `export_system_snapshot.py` |
| Modification | Never — append-only |
| Deletion | Never — retained indefinitely |
| Read authority | Point-in-time evidence; not current-state authority |
| Conflict resolution | Live state overrides snapshot; snapshot is historical |

**Reading a named snapshot:**
A named snapshot represents what the operator observed at a specific time.
It is evidence, not authority. If it contradicts the current live state,
the live state is correct — and the snapshot remains accurate for its timestamp.

| `maintenance_continuity_summary.md` | Every session | `maintenance_overview.sh` (daily) |
| `maintenance_navigation.md` | Every session | `maintenance_overview.sh` (daily) |
